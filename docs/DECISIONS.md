# 已定的决定

只记用户确认过的事。每条：日期、决定、理由。

## 2026-11-10

1. **另起新项目 Kakatta，不在 Mekke 仓库里改。** Mekke 停止开发，代码保留。
2. **项目名 Kakatta**（かかった，「上钩了！」）。和 Mekke（めっけ，「找到啦！」）一样是口语感叹，对上「闲鱼咬钩就推送」。GitHub 和 App Store 查过没有撞名。
3. **自己重写，不 fork 参考项目。** 理由见 `BACKGROUND.md`：它维护不稳、只能服务器部署；重写时吸收它踩过的坑。
4. **定位是大型、完善的开源项目**，不是自用小工具。
5. **支持多种部署方式**：服务器 Docker + 网页端；桌面客户端（Mac / Windows / Linux）自带服务端在本机运行；手机客户端（iOS / 安卓）连接自建或官方服务端。客户端可以选择监控服务在本机、自己的服务器还是官方服务器上运行。详见 `VISION.md`。
6. **对闲鱼只读、验证码交给人、频率默认值不比 Mekke §8.2 激进。** 沿用 Mekke 的账号安全底线；频率数值可以由用户修改，见第 17 条。
7. **先讨论清楚、写好文档，再开始实现。**
8. **不做官方服务端，只让用户自己部署。** 理由：官方替用户登录闲鱼、抓取数据，有法律（用户协议、「非法获取计算机信息系统数据罪」判例、个人信息保护法、ICP 备案）和成批封号的风险。用户原话：「风险大的话，那我们后面就不做官方部署的服务，只让用户自己去部署」。手机端因此只连用户自己的服务端或桌面端。
9. **目标是把东西做到足够好，不急用。** 方案一律按长期最好的做法定，不做先推给用户的简化版、过渡版（比如先做个 PWA 顶着）。用户原话：「我现在又不是急用，我现在的目标是做一个好东西出来，把它做到足够好」。
10. **开发顺序：先做服务端（Docker）和网页端，再做桌面端，最后做手机端。** 用户的 iOS 开发者账号还在申请。每一端都按最终形态做完整，不做临时版本。
11. **做官方推送中转，跟手机端一起做。** 用户授权由我来定。理由：用户自建的服务端拿不到我们 App 的推送密钥，没有中转，原生 App 就收不到推送。中转只转发端到端加密的内容，不碰闲鱼、不保存用户数据，不违背第 8 条。设计细节等做手机端时再定；服务端现在就要留好「设备配对」和「推送加密」的接口位置。
12. **技术栈：服务端用 Go，浏览器自动化用 chromedp，前端用 React + Vite + TypeScript。** 用户同意用 Go，分析见 `TECH-STACK.md`。
13. **一个服务端只有一个登录账号**：用户名加密码，登录后能设置所有东西，不做多用户、不做权限管理。用户原话：「用户大多数时候就一个人用，搞那么复杂的账号体系没有意义」。注意区分：这里说的是登录 Kakatta 的账号；用来抓取的闲鱼账号仍然可以有多个。客户端（桌面端、手机端）登录后拿到的令牌不算多账号。
14. **开源许可证：MIT。**
15. **不假定服务端在什么环境里运行。** NAS、云服务器、家里的小主机、用户自己电脑上的 Docker 都要支持。用户原话：「你不要把服务器环境假定成某个环境」。因此：
    - Docker 镜像同时支持 amd64 和 arm64；
    - 内存要省，2GB 内存的 NAS 也要能跑；
    - 不依赖公网 IP，也不假定是家用网络还是机房网络；闲鱼访问可以配代理；
    - 数据都放在一个挂载目录里，适配 NAS 常见的用户和组 ID（PUID/PGID）设置；
    - 时区可以配置。
16. **尽可能轻量：内存、硬盘、运行时占用都要小。** 用户原话：「不能说我搞进去，然后哐当一下就几个 G，比如客户端就几个 G」「不要占用太大的内存、硬盘，或者运行时之类的资源」「但是要在保证功能的前提下这样做」。前提：功能完整和账号安全优先，不为了轻量砍功能或降低防风控能力；在这个前提下选最省资源的做法。具体做法：
    - 浏览器不常驻：要运行任务时才启动，跑完就关。空闲时只剩 Go 服务端在跑。
    - 同时打开的页面数默认 1，可以调大。
    - 不另外带运行时：服务端是一个 Go 程序，桌面端也不带 Node 或 Electron。
    - 桌面端优先用电脑上已经装好的 Chrome 或 Edge，不自带浏览器。
    - 硬盘上的数据有上限：商品图片只缓存缩略图并设总量上限，旧结果按设置自动清理，日志自动轮转，限制浏览器缓存的大小。
    - 目标值（实验和实现时按实测校准，不是拍脑袋的承诺）：Docker 镜像压缩后约 300MB 以内；空闲内存 50MB 以内；跑一个页面时总内存 500MB 以内；桌面端安装包 40MB 以内。
17. **限制和参数尽量做成配置项，不写死。** 用户原话：「这种配置项我觉得可以不用写死，而是作为一个配置项，做成默认值，然后在配置下面写明为什么要这样设置、推荐的设置，以及对应的风险」「尽量做得灵活一点」。具体：
    - 频率、额度、等待时间、每次打开详情页的上限、每小时浏览次数、同时打开的页面数、缓存时长、清理周期、图片缓存上限等数值，都是配置项。
    - 每个配置项在界面上都写明：默认值、为什么这样设、推荐范围、调到推荐范围以外会有什么风险。超出推荐范围时界面给出明显提示，但允许保存。
    - 只拦明显无效的值（比如 0、负数、间隔短到 1 秒），不设「安全下限」去替用户做主。
    - 默认值按账号安全定，偏保守；由我参考上游代码和 issue 研究决定（`AGENTS.md` 的分工）。
    - 不做成配置的只有行为底线：对闲鱼只读、不破解验证码、不改浏览器指纹、不自己拼签名直接调接口。这些是做不做的问题，不是数值。


## 2026-11-10（技术和安全，由我研究后决定，作者授权）

作者原话：「技术和安全上的事，你可以多看一下参考库、多查一下资料，然后自己决策一下……能自己决定的就自己决策」。

18. **抓取与防风控按 `CRAWL-POLICY.md` 执行。** 要点：
    - 用 Google Chrome 正式版的有界面窗口，服务器上跑在 Xvfb 里；不用任何无头模式，也不用 Chromium；
    - chromedp 用固定端口、只绑定 127.0.0.1 来连接，不用 pipe，所以 `navigator.webdriver` 保持浏览器的正常值；不注入脚本，不加 blink 参数；
    - 先在首页停留，再在搜索框里输入；先用搜索结果做本地筛选，只给通过的商品打开详情页，而且有数量上限；
    - 一出现风控就结束整次运行、暂停这个账号，冷却时间逐次加倍；
    - 登录和人机验证交给用户：服务器上用 noVNC，桌面端直接把窗口调到前面；
    - 所有数值的默认值、推荐范围和风险都列在文档里。
19. **客户端连接与登录**：
    - 服务端对外只提供一套 HTTPS 接口，用 OpenAPI 描述，各端的调用代码自动生成；实时事件用 SSE；
    - 第一次打开服务端网页时设置登录账号和密码，忘记密码就用容器里的命令重置；
    - 网页端用 Cookie 会话，桌面端和手机端用令牌，令牌可以在网页端查看和吊销；
    - 手机端扫服务端网页上的二维码配对，同时交换推送密钥（第 11 条）；
    - 桌面端本机模式也走同一套接口，自动登录。
20. **AI**：
    - 分层筛：硬条件和排除词（免费）→ 文字模型看标题和描述（便宜）→ 多模态模型看图（贵），前两层通过才进入下一层；
    - 支持所有 OpenAI 兼容接口，包括本地 Ollama，可以配置多个服务商轮换；
    - 结构化输出逐级降级：JSON Schema → json_object → 纯文本宽松解析，降级过程写日志；
    - API Key 加密保存；
    - 提示词和输出格式参考 Mekke `docs/TECHNICAL.md` §11。
21. **推送渠道**：核心代码里定好统一的渠道接口。内置 Bark、Telegram、ntfy、企业微信、钉钉、飞书、PushPlus、Webhook、邮件；桌面端加系统通知，手机端加 Kakatta App 推送。不同任务可以推到不同的渠道或机器人。
22. **多语言**：简体中文和英文完整覆盖，每种语言一个 JSON 文件（照 Dalibre）；其他语言欢迎社区贡献。
23. **桌面框架用 MyGo**（作者倾向，`REFERENCES.md` 里 Dalibre 已经在用）。桌面外壳只负责窗口、托盘和启动本机服务端；万一 MyGo 停更，可以换成 Wails。
24. **桌面端本机模式**：服务端直接编译进桌面程序。抓取用电脑上已装的 Google Chrome，Windows 上没有 Chrome 就用 Edge；都没有就引导用户安装 Chrome，不自带浏览器。
25. **插件**：先在核心代码里把推送渠道和筛选规则的接口定好；核心稳定以后，再选插件运行时（候选是 Dalibre 用的 moejs，它现在是 v0.1.0）。
26. **手机端用原生**：iOS 用 SwiftUI，安卓用 Kotlin + Jetpack Compose，调用代码从 OpenAPI 生成。理由：通知操作、小组件、灵动岛这些系统能力只有原生用得好，作者也熟悉 Swift。
27. **手机在外面连家里的服务端**：由用户自己配置（公网 IP 加 HTTPS、Cloudflare Tunnel、Tailscale），文档写清每一种怎么配。不做官方的连接中转，否则所有数据都要经过我们的服务器。
28. **发布流程照 Dalibre**（`REFERENCES.md`）：
    - 推送版本标签后先建草稿；
    - 三个平台的桌面安装包加上 amd64 和 arm64 的 Docker 镜像一起构建；
    - macOS 签名并公证，更新包签名；
    - 每个版本都必须写 CHANGELOG。
29. **开发时不访问闲鱼**：用一个本地的假闲鱼页面和样例数据生成命令（照 Dalibre 的 `cmd/seed`）来开发和测试。只有动工前的实验，以及最终的人工验证，才用真实账号，并且由作者来跑。

## 2026-11-10（作者确认）

30. **设计稿用 HTML**，以后用 Claude Design 来做。第一版先不做设计，直接把功能写完，之后再做一次 Redesign。所以前端要让换皮便宜：颜色、字号、间距、圆角都用设计变量（CSS 变量），页面只组合基础组件，不在页面里写死样式（见 `TECH-STACK.md`）。
31. **Logo 沿用 Mekke 的水母**（`assets/logo/kakatta.png`，原图来自 Mekke 的 `design/app-icon/moon-jellyfish.png`）。域名和官网以后再定。
32. **GitHub 仓库**：`Seaony/Kakatta`，公开，MIT 许可证，主分支 `master`（和作者其他项目一致）。
33. **动工前的实验**：
    - 环境：作者的一台 Mac 和一台 Windows，都在家用网络里；
    - 账号：作者提供一个新注册的闲鱼账号，不是主力号，但仍要尽量不被封；
    - 新号更容易触发风控（#324、#339），所以实验按 `CRAWL-POLICY.md` 第八节的「新号实验方案」来跑：先养号，参数比默认值更保守，同一时间只在一个环境里跑。
34. **桌面端用网页界面**，和网页端共用一套前端，不用 MyGo 的原生界面。理由：网页端必须做，桌面端连远程服务端时内容也和网页端一样；只比原生界面多约 18MB 内存；一套界面，功能和修 bug 都只做一次。作者确认：「可以」。桌面端这样搭：

    - 外壳用 MyGo（Go）。它负责窗口、托盘、系统通知、选择连接哪个服务端，以及本机模式下启动内置的服务端。
    - 主窗口直接加载服务端提供的网页端：本机模式加载 `127.0.0.1` 上的地址，远程模式加载用户服务端的地址。好处有三个：
      - 和浏览器里看到的是同一个界面；
      - 界面版本永远和服务端一致，不会出现「桌面端新、服务端旧」对不上的情况；
      - 实时事件（SSE）能正常用。MyGo 文档写明，Windows 上用它自己的协议加载页面时，SSE 不能用（`frontend.md`：「Server-sent events and long polling are unsuitable there」）。
    - 只有「选择服务端」和第一次启动的引导，用打包在桌面端里的一个小页面。
    - 系统通知由外壳的 Go 代码直接订阅服务端的事件来发，不需要让远程网页调用本机能力，更安全。
    - 前端技术栈见 `TECH-STACK.md`。
    - 实现时要验证：macOS 默认不允许加载 `http://` 地址（比如局域网里的 NAS），需要在 Info.plist 里放开网页内容的这项限制。
