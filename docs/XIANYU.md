## 二、怎么读接口数据（CDP 网络事件，不注入脚本）

上游用 Playwright 的 `expect_response` 和 `page.on("response")` 读页面自己请求到的数据。Mekke 往页面里注入了一段 `capture.js`：改写 `XMLHttpRequest`、`fetch`，并包住 JSONP 回调，把网址含 `/h5/mtop.` 的响应回传给应用。Kakatta 不注入任何脚本，改用 CDP 的网络事件，下面是同一套逻辑的 CDP 写法。

### 2.1 要读的接口

所有接口都在 `h5api.m.goofish.com` 下（`config.py:22-23`），路径形如 `/h5/<接口名>/<版本>/`。

| 名称 | 网址里要含的片段 | 请求方法 | 什么时候出现 | 怎么取 | 出处 |
|---|---|---|---|---|---|
| 搜索 | `/h5/mtop.taobao.idlemtopsearch.pc.search/1.0/` | **必须是 POST** | 进入搜索结果页、每次筛选、每次翻页 | 每个动作之后取「这个动作之后的新一条」 | `search_pagination.py:14,30-37` |
| 详情 | `h5api.m.goofish.com/h5/mtop.taobao.idle.pc.detail` | 不限 | 打开详情页 | 打开之后的第一条 | `config.py:23`、`scraper.py:1034` |
| 卖家头部 | `mtop.idle.web.user.page.head` | 不限 | 打开卖家主页 | 只取第一条 | `scraper.py:418-421` |
| 卖家商品 | `mtop.idle.web.xyh.item.list` | 不限 | 卖家主页默认的商品标签 | 第一条（我们不滚动，只有第一页） | `scraper.py:430-433` |
| 卖家评价 | `mtop.idle.web.trade.rate.list` | 不限 | 点「信用及评价」标签后 | 第一条（同样不滚动） | `scraper.py:441-444` |

上游判断网址用的是响应的网址（`response.url`），也就是跳转之后的最终网址。

另外，**网址含 `/h5/mtop.` 的所有响应**都要做风控检查（第四节），不管是不是上表里的接口。这和 Mekke `capture.js` 的过滤条件一样。

### 2.2 事件流程

开启 `Network.enable` 后，一次接口请求会依次收到这些事件，用 `requestId` 串起来：

1. `Network.requestWillBeSent`：请求发出。这里有 `request.url`、`request.method`、`type`（`XHR`、`Fetch`、`Script` 等）、`frameId`。如果带 `redirectResponse`，说明同一个 `requestId` 发生了跳转，用新的网址覆盖旧的。
2. `Network.responseReceived`：收到响应头。这里有 `response.url`、`response.status`、`response.headers`。**风控响应头 `bxpunish` 在这里查**（第四节）。
3. `Network.loadingFinished`：正文收完。**只能在这之后**调用 `Network.getResponseBody(requestId)` 取正文；返回的 `base64Encoded` 为真时先解码。
4. 或者 `Network.loadingFailed`：请求失败（`errorText`、`canceled`），没有正文。

注意（`CRAWL-POLICY.md` 第二节「chromedp 的坑」）：

- 事件回调里不能阻塞，也不能发 CDP 命令；取正文放到单独的 goroutine。
- 页面跳转后，浏览器会丢掉旧页面的正文缓存，`getResponseBody` 会报找不到资源。所以 `loadingFinished` 一到就取，不要等到要用时再取。
- 接口正文只放在内存里，最多保留最近 200 条（Mekke 的做法）。不写进日志、不落盘。唯一的例外见 6.2 节的调试开关。

### 2.3 判断是不是这一次操作的响应

做法和上游的 `expect_response`、Mekke 的 `mark()` / `next(after:)` 一样：**先记下位置，再操作，再等位置之后的新响应**。

1. 每条请求在 `requestWillBeSent` 时分配一个递增编号。
2. 操作之前调用 `Mark()`，记下当前编号。
3. 操作（点击、按回车、打开网址）。
4. 等第一条同时满足这些条件的请求：编号大于 `Mark()`；网址含该接口的片段；请求方法符合（搜索必须是 POST）；已经 `loadingFinished` 并取到正文。
5. 正文先做外壳检查（2.4 节）。令牌过期的那条不算，继续等下一条。

**为什么按「请求发出」编号，而不是按「响应收到」编号**：如果按响应到达的先后编号，一个在操作之前就发出、操作之后才返回的旧请求，会被误认成这次操作的结果。所以编号必须在 `requestWillBeSent` 时分配，不能等取到正文时才分配。

**还能知道「请求到底发没发出去」**：注入脚本只能看到响应，CDP 能看到请求本身。所以等待超时的时候要分两种情况：

- 操作之后**根本没有发出**匹配的请求：说明点击没生效，可以按各步骤的规则重试。
- 请求**已经发出、只是还没返回**：继续等它，**不要再点一次**。开关类筛选（个人闲置、包邮）再点一次就会取消筛选；「下一页」再点一次会跳过一页。

所以等待接口要提供两个结果：「等到了响应」和「`Mark()` 之后有没有发出过匹配的请求」。

**筛选时取最后一条**：一次筛选里页面可能连发几次搜索请求，上游只用最后一次筛选拿到的响应作为第 1 页（`scraper.py:970-974`）。怎么判断是最后一条：拿到第一条匹配的响应后，1.5 秒内没有新的匹配请求发出，才定为最后一条；这期间发出了新的匹配请求，或者还有匹配请求在路上没返回，就等它回来，再从它开始重新等 1.5 秒。

### 2.4 响应外壳：`ret` 字段

闲鱼的接口（mtop）业务失败时 HTTP 状态码通常还是 200，所以必须看正文顶层的 `ret` 字段：它是一个字符串数组，成功时第一项以 `SUCCESS` 开头。上游的检查方式是把整个 `ret` 转成字符串再找子串（`scraper.py:1046-1049`）。

| `ret` 里任一项含 | 含义 | 处理 |
|---|---|---|
| `FAIL_SYS_USER_VALIDATE` | 需要人机验证 | 风控，见第四节 |
| `RGV587` | 需要人机验证 | 风控，见第四节 |
| `FAIL_SYS_SESSION_EXPIRED` | 这条接口的会话失效 | 本次操作的目标接口才按登录失效停手；旁路接口只记观察，见第四节 |
| `FAIL_SYS_TOKEN_EXOIRED`（mtop 原样拼错）、`FAIL_SYS_TOKEN_EXPIRED`、`FAIL_SYS_TOKEN_EMPTY` | 令牌过期。页面会自己刷新令牌并重发请求 | 忽略这条，继续等同一条件的下一条；不算登录失效 |
| 其他情况下第一项不以 `SUCCESS` 开头 | 业务失败 | 只让**正在等这个接口**的那一步失败（普通失败）；其他接口的业务失败不影响当前步骤（Mekke 的修正：无关接口出错曾经把正在等的搜索也弄失败了） |

另外：

- HTTP 状态码不是 2xx 时，上游直接当失败处理（`scraper.py:989,1043`）。
- 上游测试样例（`tests/fixtures/*.json`）是手写的，没有 `ret` 字段，卖家商品和评价样例的根还是数组。解析函数要能吃这些样例；但在真实响应入口，`ret` 缺失要当成解析失败。
- Mekke 还把 `FAIL_SYS_TRAFFIC_LIMIT`、`FAIL_SYS_FLOWLIMIT` 当成「被限流」并换账号重试。这两个码上游源码里没有，是 Mekke 按 mtop 常见返回猜的。Kakatta 不因为它们换账号（`PRODUCT.md` 第 2 节只在登录失效时换号），按上表最后一行当业务失败处理。

### 2.5 JSONP

Mekke 的注入脚本额外处理了 JSONP（mtop 有时用 `<script>` 标签加 `callback=` 参数请求，正文是 `回调名({...})`）。上游对上表五个接口都直接 `response.json()`（`scraper.py:423,432,443,1044`、`scraper.py:993-994`），说明这些接口返回的是纯 JSON。

为了稳妥，解析正文时：如果第一个非空白字符不是 `{` 或 `[`，而是「标识符 + `(`」，就去掉开头的 `回调名(` 和结尾的 `)` 或 `);` 再解析。用 CDP 时 JSONP 请求的 `type` 是 `Script`、方法是 GET，所以它不会被当成搜索接口（搜索要求 POST）。

### 2.6 其他

- **iframe**：上表的接口都由主页面发出。登录框（`#alibaba-login-box`，第八节）是 iframe，如果它是跨域的，在 Chrome 里会是独立进程，主页面的 `Network` 事件看不到它的请求。登录判断不依赖它的请求，所以不需要额外挂接。
- **调试日志**：chromedp 的协议调试输出（`WithDebugf` 之类）会把所有 CDP 消息打出来，里面有接口正文和 `Network.getCookies` 返回的 Cookie 值。正式代码和实验程序都不能打开它。

## 三、怎么找元素和操作页面（不注入脚本）

找元素只用 `DOM`、`CSS` 这些 CDP 域的查询命令，不用 `Runtime.evaluate` 在页面里跑代码。点击和输入用 `Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`、`Input.insertText`。

### 3.1 找元素

| 要找的 | 做法 |
|---|---|
| CSS 选择器 | `DOM.getDocument` 拿到根节点，再 `DOM.querySelectorAll`。页面变化后（收到 `DOM.documentUpdated`）旧的节点 ID 失效，每次查询都重新取根节点 |
| XPath | `DOM.performSearch` 接受 XPath（chromedp 的 `Search` 就是它），用完调 `DOM.discardSearchResults` |
| 按文字找 | 用 XPath `//*[normalize-space(.)='新发布']` 找出所有文字完全等于目标的元素，去掉「子孙里还有匹配元素」的那些，剩下最深的一层；再只留可见的，取文档顺序里的第一个 |
| 元素里面的子元素 | `DOM.querySelectorAll(父节点 ID, 选择器)`，和网页里 `element.querySelectorAll` 一样，所以 `:scope > div` 可以用 |
| 页面上有没有某段文字 | `DOM.performSearch` 直接传普通文字，逐个看命中的节点：命中的是文字节点时看它的父元素。这个元素要可见，并且它和它的祖先都不是 `script`、`style`。至少有一个这样的节点才算出现。只看结果数会把脚本、样式里的同样文字也算进去 |

**可见**的判断（照 Mekke 的 `isVisible`）：`DOM.getBoxModel` 能拿到盒模型且宽高都大于 0；再用 `CSS.getComputedStyleForNode` 确认 `visibility` 不是 `hidden`、`display` 不是 `none`、`opacity` 不是 `0`。只查盒模型不够：透明度为 0 的元素会被误认为可见，风控遮罩检查要用完整的判断。

**上游的「按文字找」和我们的区别**：上游的 `page.click("text=新发布")` 是 Playwright 的文字选择器（不区分大小写、按包含匹配，点第一个匹配）；`get_by_text("区域", exact=True)` 是完全相等。Mekke 统一用「完全相等的最深元素」。我们照 Mekke：闲鱼这几个筛选文字都很短，完全相等更不容易点错。

**同一段文字可能出现在好几个地方**：「包邮」也会出现在商品卡片的标签里，「最新」也可能出现在别处。上游点的是文档里的第一个匹配，等于假定筛选栏在商品列表上面。Kakatta 先照这样做；2026-11-11 已观察「新发布」及「最新」各自父元素的类名前缀，尚未证明覆盖整条筛选栏。完整范围确认后再限定查找，不把单个入口的父元素当作整栏。

### 3.2 点击

1. 元素不在可视区域时先滚过去：用滚轮事件（3.4 节）滚到元素进入视口；`DOM.scrollIntoViewIfNeeded` 也可以，它不经过页面脚本，但页面只看到滚动、看不到滚轮。
2. 用 `DOM.getBoxModel` 取元素位置，在元素中间区域随机取一个点。
3. `Input.dispatchMouseEvent`：先分几步 `mouseMoved` 移过去，再 `mousePressed`（左键、`clickCount: 1`），停一下，再 `mouseReleased`。移动的步数、每步的停顿、按下到抬起的间隔（60–160 毫秒；Mekke 是 60–140 毫秒）都照 `CRAWL-POLICY.md` 第六节「单个动作内部的细节」。
4. 点击前后都做一次风控检查（第四节）。

### 3.3 输入文字和按键

- 英文、数字：每个字一对 `Input.dispatchKeyEvent`（`keyDown` 带 `text`，然后 `keyUp`）。
- 中文等：`Input.insertText`，每次一个字。Chrome 官方对它的说明就是「模拟不是由按键产生的输入，比如表情键盘或输入法」，接近真人用输入法上屏。真人用输入法时页面还会收到组合输入事件（`compositionstart` 等），`insertText` 不产生这些。闲鱼会不会检查这一点，没有证据。
- 每个字之间的间隔：按 `CRAWL-POLICY.md` 第六节的配置项「搜索框输入每个字的间隔」。价格框里输入数字也用这个间隔。
- 回车：`key: "Enter"`、`code: "Enter"`、`windowsVirtualKeyCode: 13`、`keyDown` 时带 `text: "\r"`。Tab：`key: "Tab"`、`code: "Tab"`、`windowsVirtualKeyCode: 9`。
- 清空输入框：点进去后按 Ctrl+A 全选（Chrome 跑在 Linux 容器里，只用 Ctrl；`dispatchKeyEvent` 的 `modifiers` 里 Ctrl 是 2），再按 Backspace（`windowsVirtualKeyCode: 8`）。
- **读输入框里现在的值**：不跑脚本就读不到 `value` 属性（`DOM.getAttributes` 只能拿到 HTML 里写的初始值）。用 `Accessibility.getPartialAXTree` 取这个输入框的无障碍节点，它的 `value` 就是当前显示的值。实现时先在本地假页面里验证能读到。

### 3.4 滚动

用 `Input.dispatchMouseEvent` 的 `mouseWheel` 事件，带 `deltaY`，分 3–5 下滚完，每下之间的停顿照 `CRAWL-POLICY.md` 第六节。不用 `window.scrollBy`，那要在页面里跑脚本。

### 3.5 等页面加载

上游所有 `goto` 都用 `wait_until="domcontentloaded"`，不等全部资源加载完（`scraper.py:457,694,715,1038`）。Kakatta 也一样：

- `Page.setLifecycleEventsEnabled(true)` 之后，等主框架的 `Page.lifecycleEvent`，`name` 为 `DOMContentLoaded`，并且 `loaderId` 是这次导航的。
- 用 `Page.navigate` 打开时，它直接返回 `loaderId`；返回里有 `errorText` 就是导航失败。
- 由点击或回车引起的跳转，先等主框架的 `Page.frameNavigated`（编号在操作之后、网址符合预期），拿它的 `loaderId`，再等对应的 `DOMContentLoaded`。
- 按 `loaderId` 对应，是为了不把上一次导航、或者 iframe 的加载完成当成这一次的（Mekke 实际踩过这个坑）。

不用 `chromedp.Navigate` 来等：它等的是整页 `load` 事件，比上游晚，页面上有长时间不结束的请求时还可能一直等到超时。

## 四、风控信号：查什么、什么时候查、在哪里查

信号和处理方式以 `CRAWL-POLICY.md` 第四节为准，这里补上每个信号的具体位置和检查时机。一旦命中，按那一节的规则立即结束整次运行，并一路传到最外层，不能被任何一层的普通错误处理吞掉。

### 4.1 什么时候查

| 时机 | 查哪些 |
|---|---|
| 每次导航到 `DOMContentLoaded` 之后 | 主框架网址、验证遮罩、页面文字 |
| 收到主框架页面文档本身的响应（`Network.responseReceived` 里 `type` 为 `Document`、`frameId` 是主框架） | 响应头 |
| 每次点击、按键之前和之后 | 主框架网址、验证遮罩。逐字输入关键词或价格时例外：不在每次按键前后查，整段输入之前和之后各查一次 |
| 每收到一条网址含 `/h5/mtop.` 的响应 | 响应头、`ret`、`data.url`；**同时再查一次验证遮罩**（Mekke 发现：接口返回成功、页面却弹出遮罩时，只查接口会漏掉） |
| 等元素、等接口超时的时候 | 主框架网址：上游在超时时先看是不是跳到了登录页，是的话报登录失效，不是才报超时（`scraper.py:728-733,1200-1206`） |

上游只在搜索结果页加载后查一次遮罩，每个遮罩最多等 2 秒（`scraper.py:739-785`）；接口 `ret` 只查详情接口（`scraper.py:1046-1049`）。Kakatta 照 Mekke 每一步都查。

- 上游检测到验证后会先睡 3–60 秒再退出（`scraper.py:1056-1060`）。Kakatta 不睡，立即结束。

## 五、搜索流程

一次运行的整体顺序见 `CRAWL-POLICY.md` 第三节。这一节写前四步在页面上具体怎么做。

**额度**：每一次打开页面、每一次会触发搜索请求的点击之前，都要先向节奏控制申请额度，申请不到就停下（5.8 节列出每个动作会产生什么请求）。

### 5.1 首页

1. `Mark()`，`Page.navigate` 打开 `https://www.goofish.com/`，等 `DOMContentLoaded`（30 秒，`scraper.py:692-696`）。做风控检查。
2. 停留，按配置项「首页停留」。
3. 用滚轮向下滚一次，滚 200–700 像素。上游也是这个范围（`scraper.py:701` 的 `Math.random() * 500 + 200`），但用的是 `window.scrollBy`；我们用滚轮事件（3.4 节）。
4. 再停一下，按配置项「普通操作之间等待」。上游两次各等 1–2 秒（`scraper.py:698,702`）。

### 5.2 在搜索框里输入

上游和 Mekke 都是直接打开搜索网址，没有搜索框的选择器，所以下面的搜索框选择器和回车后的行为都**待用真实页面确认**（确认方法见第十一节）。流程本身是确定的：

1. 找到首页顶部的搜索框，确认可见。
2. 用鼠标点进去（3.2 节）。搜索框里如果已经有文字（比如推荐词），先清空（3.3 节）。推荐词如果只是 placeholder，不用清。
3. 逐字输入关键词（3.3 节），每个字的间隔按配置项「搜索框输入每个字的间隔」。
4. 停一下，按配置项「普通操作之间等待」。输入过程中可能弹出联想词列表，不去点它。
5. `Mark()`，按回车。

### 5.3 等搜索结果页

1. 等主框架跳到网址含 `/search` 的页面（`Page.frameNavigated`），再等它的 `DOMContentLoaded`（60 秒，照上游打开搜索页的超时，`scraper.py:715`）。
   - 如果回车后是**新开了一个标签页**（待用真实页面确认），要在浏览器上开 `Target.setAutoAttach`（`autoAttach: true`、`waitForDebuggerOnStart: true`、`flatten: true`），新标签页一出来先暂停，挂上 `Network.enable` 后再让它继续，否则会漏掉第一条搜索请求。之后在新标签页里操作，搜索结果页加载完后关掉首页那个标签页，保证同一时间只有一个闲鱼页面（同一账号同时只开一个页面，`CRAWL-POLICY.md` 第六节）。
2. 等 `Mark()` 之后的第一条搜索接口响应（POST，30 秒，`scraper.py:711-713`）。
3. 检查主框架网址是不是登录页（`scraper.py:717-720`），再做完整的风控检查。
4. **核对关键词**：从结果页网址里取 `q` 参数（按网址规则解码），和任务的关键词比较。比较前两边都先做 NFKC，再把连续空白合并成一个空格、去掉首尾空白，避免全角半角、多打的空格被当成不一致。不一致说明输入出了问题（比如中文输入没有完整上屏），这次运行按普通失败结束，不拿错误关键词的结果继续。
5. 等文字 `新发布` 出现（15 秒，`scraper.py:727`）。超时先看是不是掉了登录；不是就按「页面结构变了」普通失败（`scraper.py:728-733`）。

### 5.4 关广告

在 3 秒内找可见的 `div[class*='closeIconBg']`，找到就点，找不到就跳过（`scraper.py:788-792`）。关广告一般不产生接口请求（5.8 节），不计入访问额度（`DOMAIN.md` 第 0 节）。

### 5.5 筛选

依次做发布时间、个人闲置、包邮、地区、价格。每一步都是：`Mark()` → 操作 → 等**一条新的**搜索接口响应（20 秒，`scraper.py:800-802` 等处）。全部做完后，用最后一条响应作为第 1 页（2.3 节）。

每次点击之间按配置项「普通操作之间等待」。上游各处的等待是 1–2、1.5–2、2–3、2–4 秒不等（`scraper.py:799,805,820,829,841,884,901-911,923,948,963`），Kakatta 统一用这个配置项。

**没等到响应怎么办**（照 Mekke，比上游严格）：

| 类型 | 步骤 | 处理 |
|---|---|---|
| 可以重复做的 | 发布时间、地区、价格（重复做结果一样） | 先看 `Mark()` 之后有没有发出搜索请求：发出了就继续等，最多再等 10 秒；没发出，等「普通操作之间等待」后重做一次。还不行，这一步失败 |
| 开关类 | 个人闲置、包邮（再点一次会取消） | **绝不重复点击**。发出了请求就最多再等 10 秒；没等到就这一步失败 |

任何一步失败，**整次运行按普通失败结束，不带着没筛完的结果继续**（`CRAWL-POLICY.md` 第三节第 3 步）。尤其「个人闲置」没法在本地补筛（5.7 节），这一步失败时绝不能拿未筛选的结果去判断。

上游的处理不同：发布时间、包邮、地区失败都只写一条日志然后继续（`scraper.py:807-812,831-834,933-936`），只有个人闲置超时会让整次运行失败（`scraper.py:814-821` 没有捕获超时）。

各步骤：

1. **发布时间（每次都做，一律点「最新」）**：点文字 `新发布`，等「普通操作之间等待」，在弹出的菜单里点 `最新`（`scraper.py:796-806`）。菜单的容器待用真实页面确认，确认前取文档里第一个可见的完全匹配。
   - 任务设了「1 天内」「3 天内」这类时间范围，页面上也只点「最新」，时间范围完全交给本地补筛（5.7 节）。理由：页面上的「N 天内」选项（`1天内`、`3天内`、`7天内`、`14天内`，`TaskForm.vue:423-427`）选了以后是否还按最新发布排序，没有依据；而「每次运行翻几页」默认 1 页，前提就是按最新发布排序（`CRAWL-POLICY.md` 第六节）。
   - 上游只在任务设置了发布时间时才做，并点对应的「N 天内」（`scraper.py:796`）；Mekke 每次都做，不限时间时选「最新」。
2. **个人闲置**（任务开启时）：点文字 `个人闲置`（`scraper.py:814-821`）。
3. **包邮**（任务开启时）：点文字 `包邮`（`scraper.py:823-834`）。
4. **地区**（任务设置了才做）：
   1. 点文字完全等于 `区域` 的元素（`scraper.py:838-840`），等「普通操作之间等待」。
   2. 找地区弹层（3.6 节的规则，`scraper.py:842-858`），等它可见（5 秒，`scraper.py:859`）。
   3. 取弹层里第一个可见的 `[class*='areaWrap']`（3 秒，`scraper.py:862-865`），它的直接子元素第 0、1、2 个分别是省、市、区三列。
   4. 任务里的地区写成 `省/市/区`，按 `/` 拆开、去掉首尾空白（`scraper.py:871-873`）。在每一列里找文字完全等于目标值的可见 `[class*='provItem']` 点击（`scraper.py:875-911`）。每次点击后等「普通操作之间等待」，等新的一列出现再点下一列。
   5. 区一列存在、但里面没有任何可见选项时，跳过这一列（Mekke 的做法：有些地区没有第三级）。其他情况下找不到目标选项，这一步失败。上游是写一条日志跳过（`scraper.py:894-895`）。
   6. 点击提交按钮（3.6 节，`scraper.py:913-924`），等新的搜索响应。
   - **地区名称**：要和闲鱼页面上的文字完全一样。上游把页面上的地区整理成了 `web-ui/src/data/goofishRegions.json`（MIT，可以直接复制使用，注明出处）：省份不带「省」「市」后缀（如 `广东`、`北京`），城市同样不带（如 `深圳`），每个省、市下第一个选项是「全某某」（如 `全广东`、`全广州`），还有 `全国`（下面是 `全国`、`珠三角`、`江浙沪`、`京津冀`、`东三省`）和 `海外`。上游保存任务时会去掉每一段末尾的「省」「市」（`TaskForm.vue:234-242`），选了省份会自动把城市设为「全某某」（`TaskRegionSelector.vue:80-101`）。
   - **本地复核地区**（5.7 节）时这些特殊选项的对应关系，以 `DOMAIN.md` 5.1 为准：选「全国 / 全国」或「海外」时不做本地复核；选「全国」下的「江浙沪」「珠三角」「京津冀」「东三省」时，各对应一组省名，商品地区含其中任一省名就算在范围内；市名以「全」开头（如「全广东」）时只比省名；商品地区只有市名时用地区数据反查省名。
5. **价格**（设置了最低价或最高价才做）：
   1. 找价格输入区，不可见时这一步失败（上游是写日志跳过，`scraper.py:942,965-966`）。
   2. 点第 0 个输入框，清空，输入最低价；等「普通操作之间等待」。再对第 1 个输入框输入最高价。没设置的那一端不动（`scraper.py:943-956`）。
   3. 数字的写法：整数不带小数点（5000 写成 `5000`，不能写成 `5000.0`）；有小数时原样写。Mekke 踩过的坑：整数被写成 `5000.0` 后，页面去掉小数点变成了 `50000`。
   4. `Mark()`，按 Tab 提交（`scraper.py:958-961`）。
   5. 等新的搜索响应，最多 20 秒（上游）。如果 8 秒内**根本没有发出**搜索请求，就点回最后填的那个输入框，按一次回车（Mekke 的第二次尝试），再等 20 秒。
   6. 收到响应后读两个输入框当前的值（3.3 节），和目标值比较（按数值比较，页面显示成 `5000.00` 也算对）。不一致就这一步失败。

### 5.6 翻页

每次运行最多翻到配置项「每次运行翻几页」。

1. 用下一页选择器找按钮（`search_pagination.py:9-13,49-52`），找不到就停止翻页。
2. 等配置项「页与页之间等待」（上游是 10–15 秒，`scraper.py:1193-1198`）。
3. 滚到按钮可见（`search_pagination.py:56`），`Mark()`，点击（上游点击超时 10 秒，`search_pagination.py:16,62`）。
4. 等新的搜索响应（20 秒，`search_pagination.py:15,57-60`），然后等「普通操作之间等待」（上游 2–5 秒，`search_pagination.py:19-20,69-72`）。
5. 没等到时：上游等 5 秒后**再点一次**，最多两次（`search_pagination.py:17-18,77-87`）。Kakatta 先看有没有发出请求：发出了就继续等，最多再等 20 秒；没发出才重点一次，重点前等「普通操作之间等待」。还是失败就停止翻页，保留已经读到的页，只记一条警告，这次运行仍算成功（风控和登录失效除外，照第四节结束运行）。
6. 某一页解析出 0 个商品就停止翻页（`scraper.py:996-997`）。

### 5.7 本地补筛

页面上的筛选可能没生效，所以解析之后要在本地再筛一遍（Mekke 的做法）。规则以 `DOMAIN.md` 5.1（第一层）为准，包括价格、包邮、发布时间、地区怎么判，以及价格或发布时间解析不出来时不排除；被补筛掉的商品怎么处理以 `DOMAIN.md` 4.4、4.7 为准：价格照样记录，AI 任务里照样进第二层抽规格，用于比价，但不改变它们被排除的结论。

这里只补两条和页面有关的：

- 包邮看 9.2 节的「包邮」标签（`args.tag` 等于 `freeship`）。
- 个人闲置：搜索结果里没有能判断的字段，只能依赖页面筛选（所以 5.5 节要求它失败时整次运行失败）。

发布时间的「N 天内」只在这里判断，页面上一律点「最新」（5.5 节）。

### 5.8 每个动作会产生什么请求

用来对照 `CRAWL-POLICY.md` 第六节的访问上限计数：

| 动作 | 对闲鱼产生的请求 |
|---|---|
| 打开首页 | 一次页面加载 |
| 搜索框回车 | 一次页面加载 + 一次搜索接口 |
| 关广告 | 一般没有接口请求 |
| 点「新发布」打开菜单 | 一般没有；点选项后一次搜索接口 |
| 点个人闲置、包邮 | 各一次搜索接口 |
| 地区：点「区域」、点省、点市、点区 | 打开弹层、点省市区时会不会请求待用真实页面确认（弹层上显示「查看 N 件宝贝」，说明可能在请求数量）；点提交后一次搜索接口 |
| 价格：按 Tab 或回车 | 一次搜索接口 |
| 翻一页 | 一次搜索接口 |
| 打开详情页 | 一次页面加载 + 一次详情接口 |
| 打开卖家主页 | 一次页面加载 + 头部和商品接口；点评价标签再加一次评价接口 |

Mekke 的计数口径最保守：首页、搜索页、每一次筛选点击（包括打开菜单、地区的每一次点击、价格框的聚焦和提交）、关广告、每次翻页和重试，都在动作之前各算一次搜索类访问；登录时打开首页也算一次；打开详情页、卖家主页、自己的主页各算一次详情类访问。

## 六、详情流程

只给通过本地筛选的商品打开详情页，每次运行的数量和每天的额度见 `CRAWL-POLICY.md` 第六节。打开之前先申请详情类额度，申请不到就把剩下的商品留到下次。

### 6.1 步骤

1. 等配置项「打开详情前等待」（上游 2–4 秒，`scraper.py:1029`）。
2. `Mark()`，在**同一个标签页**里 `Page.navigate` 打开详情链接（25 秒），等 `Mark()` 之后的第一条详情接口响应（25 秒，`scraper.py:1033-1040`）。上游每个商品新开一个页面，看完关掉（`scraper.py:1031,1188-1189`）；我们只用一个标签页（`CRAWL-POLICY.md` 第六节）。
3. 风控检查。HTTP 状态码不是 2xx 时这个商品失败（`scraper.py:1043,1168-1171`）。检查 `ret`（2.4 节）。
4. 解析（9.3 节）。
5. 停留，按配置项「看完详情后停留」（上游 5–10 秒，再加关页面后的 2–4 秒，`scraper.py:1167,1191`）。

### 6.2 失败怎么处理

- 风控和登录失效：结束整次运行（第四节）。上游在这里有 bug：风控异常被外层的通用 `except Exception` 吞掉了，日志说程序终止，实际继续打开下一个商品（`scraper.py:1065` 抛出，`scraper.py:1186-1187` 吞掉；`CRAWL-POLICY.md` 第四节）。我们要有专门的测试保证不会这样。
- 其他失败（超时、解析失败、业务失败）：只算这个商品失败，继续下一个；同一个商品失败 3 次后不再自动重试（Mekke 的做法）。
- **失败诊断**：详情的描述字段路径还没确认（9.3 节）。成功解析时用观察事件报告命中的字段路径；仅解析失败时，把触发失败的那一条接口正文随当前页面诊断包保存在本机，隐去凭据和明确账号身份字段，不保存成功响应。数量、大小和导出限制见 `DECISIONS.md` 第 128 条。

## 七、卖家流程

AI 任务在卖家资料没有缓存或缓存已过期时打开卖家主页，关键词任务不打开（`DOMAIN.md` 4.9、`CRAWL-POLICY.md` 第三节第 7 步）。

1. 先查本地缓存：同一个卖家在配置项「卖家信息缓存」的时长内抓过，就直接用，不打开页面，也不占额度。上游是内存缓存，默认 1800 秒（`scraper.py:281-284`、`seller_profile_cache.py:23-29`）；Kakatta 存进数据库，默认 24 小时。
2. 申请一次详情类额度，并占用一个「每次运行最多打开几个详情页」的名额（卖家主页和详情页合计，`DOMAIN.md` 4.9）。
3. `Mark()`，`Page.navigate` 打开 `https://www.goofish.com/personal?userId=<sellerId>`（20 秒，`scraper.py:455-459`），等第一条卖家头部响应（15 秒，`scraper.py:460`）。
4. 等「普通操作之间等待」（上游 2–4 秒，`scraper.py:465`）。取 `Mark()` 之后的第一条卖家商品响应，最多再等 8 秒（`scraper.py:469`）。商品接口可能在头部之前就返回了，所以 `Mark()` 要在打开页面之前记。
5. **不滚动加载更多**（`CRAWL-POLICY.md` 第三节第 7 步）。上游会反复滚到页面底部，直到接口返回的 `data.nextPage` 为假或 8 秒没有新数据（`scraper.py:435,446,466-472,482-488`）。
6. 找 XPath `//div[text()='信用及评价']/ancestor::li`（`scraper.py:477-478`）。点之前申请一次详情类额度；它不是新页面，不额外占「每次运行最多打开几个详情页」的名额。额度申请不到就不点，评价留空。申请到了就 `Mark()`，点击，等「普通操作之间等待」（上游 3–5 秒，`scraper.py:480`），取第一条评价响应（8 秒）。找不到这个标签就跳过评价（`scraper.py:493-494`）。同样不滚动。
7. 解析（9.4 节），写入缓存。

卖家流程遇到普通失败时，失败的部分留空，已取得的资料照常保留。商品继续判断，失败步骤记一条警告。遇到风控或登录失效则按第四节停止。

**卖家 ID 从哪来**：只有详情接口里有（`data.sellerDO.sellerId`，`scraper.py:1117`）。上游的搜索结果解析不读卖家 ID，所以「屏蔽卖家」在打开详情之前只能靠以前抓过详情时记下的「商品 → 卖家」对应关系（Mekke 的做法）。搜索接口里有没有卖家 ID 字段，待用真实页面确认。

## 八、登录与账号资料

### 8.1 账号和浏览器

- 每个闲鱼账号一个独立、长期保留的浏览器配置目录（`CRAWL-POLICY.md` 第二节）。登录状态由 Chrome 自己保存和续期。
- Kakatta **不导入、不导出 Cookie**，也**不读取、不记录、不打印 Cookie 的值**，只能检查某个 Cookie 在不在（`PRODUCT.md` 第 14 节）。
- 账号绑定了代理时，登录也走同一个代理。Mekke 登录不走代理，但 Kakatta 每个账号固定一个代理，登录时换 IP 反而不正常（`PRODUCT.md` 第 2 节，#492）。
- 退出登录或删除账号：关掉浏览器后删除这个账号的配置目录。

### 8.2 登录步骤

**扫码登录和过验证的会话当成一次运行处理**。过验证的会话指用户点「去验证」后重开的浏览器，以及运行中出现验证后保留的浏览器在用户打开远程画面之后的那段（`CRAWL-POLICY.md` 第四节）。

- 和这个账号的任务互斥：同一账号的任务和会话不同时进行。
- 占一个全局页面名额，没有空名额时等前面的运行结束。
- 10 分钟没完成就关掉浏览器，账号状态不变，用户可以再开一次。
- 访问额度用完时也允许开始（这是用户主动操作），程序打开的页面照样计数。

步骤：

1. 用这个账号的配置目录启动有界面的 Chrome，打开 `https://www.goofish.com/`（30 秒）。和 Mekke 一样，打开首页也计入搜索类访问。
2. 让用户看到这个窗口（通过网页端里的 noVNC 远程画面，`CRAWL-POLICY.md` 第五节），提示：「点击页面右上角的『登录』，用闲鱼 App 扫码」。
3. 用户自己点登录、扫码；遇到短信验证、「保持登录」确认，也由用户自己处理。程序不点登录框里的任何东西。
4. 程序每秒检查一次登录是否完成（8.3 节）。这些检查只读本地的浏览器状态，不访问闲鱼。
5. 完成后取昵称（8.4 节），关闭浏览器。

登录过程中出现验证码时，就留在这个登录窗口里让用户处理，不另开验证窗口，也不算成任务运行的风控（Mekke 的做法）。

### 8.3 怎么判断登录成功

两边的做法：

- **上游现在**：没有应用内登录。用户在自己的浏览器里登录闲鱼，用浏览器扩展把全部 Cookie 导出成 JSON 文件（`chrome-extension/background.js:246-258,260-289`），上游只检查文件在不在（`src/api/routes/settings.py:221-222`）。登录是否失效，要等任务运行时被跳到登录页才知道（`scraper.py:717-720`）。
- **上游旧登录脚本**：点登录入口后等登录框 iframe `#alibaba-login-box` 出现；用户扫码后，出现「保持登录」按钮就点它，或者等登录框从页面上消失（`state="detached"`），就认为登录完成，然后保存 Cookie（`login.py@de3d6da:127-141,145-159`）。
- **Mekke**：每秒检查一次：域名是 `goofish.com` 或它的子域名、名为 `unb`、值不为空的 Cookie 是否存在。存在就算登录成功。这个 Cookie 名在上游里**没有依据**，Mekke 也没用真实账号确认过。

Kakatta 采用本次人工会话的页面变化和已确认的用户昵称节点（第 131、132 条）：

1. 主框架不是登录页，没有可见验证码、环境异常或直接拒绝。
2. 本次会话先观察到可见的 `#alibaba-login-box`，之后它不可见。
3. 从最近一次观察到登录框仍可见时的采样起点之后，主框架发生导航，或者主页面重新发起 mtop 请求。只关框不够，扫码前的旧请求或旧成功也不够；不要求 `loginuser.get`、`page.nav` 返回成功，它们的会话失效仍只作观察。
4. 规则中的首页用户昵称节点可见，去掉首尾空白后非空，且不是「登录」。头像在未登录时也存在，不能代替该节点。

满足后继续原计划的一次自己的主页读取；这组变化是扫码流程的证据，不能宣称永久登录有效。直接拒绝和环境异常仍立即结束，验证码留在同一画面处理。只确认已经收到的具体验证信号，不跳过在途响应；用户关闭窗口或超时照常结束。

**`unb` 不作成功依据**：2026-11-11 真实复测中，旧 `unb` 仍存在，但页面尚未弹出延迟登录框，程序曾在等待 250 毫秒后误判成功。没有看到失效响应、当前没有登录框、存在 `unb`、任意旧接口成功，都不能证明已登录。程序不再读取任何 Cookie 的值。

**本来已经登录的页面**：本会话从未见过登录框时，经过同样的页面安全检查，且已确认的用户昵称节点成立，才可完成。该分支不能把尚未解决的验证码响应当作已处理；缺少节点、空文字、文字仍为「登录」或读取失败都继续等待。规则第 4 版加入上述昵称选择器；只读本地 DOM，不增加页面访问。

**每次运行的本地预检**：启动 Chrome 后、打开首页前，只按名字记录 `unb` 是否存在，缺失只记警告；存在也不能证明会话有效。登录是否失效以首页主框架、可见登录框及本次目标接口为准（第四节）。

**用户区证据**：`login_header` 观察按 `after_home`、`waiting`、`after_login`、`after_own_profile` 分开保存。只记候选范围、标签层级、类名前缀、属性名、可见性、是否含「登录」及头像候选等布尔，不记昵称原文、用户编号、图片地址或属性值。资料页的观察明确标为资料页阶段，不能冒充已登录首页样本。找不到节点或读取失败都不参与放行。

**重开浏览器的登录证据**：实验在 Chrome 启动后、任何导航前，以及扫码成功后、取自己资料前，各记录一次整个配置的 Cookie 名称、域、是否会话 Cookie、到期时间（CDP Unix 秒）。不读、不保存值，也不保存完整协议对象。读取失败标记「未知」，不能伪装成空列表。摘要保留 `after_startup`、`after_login` 两个阶段，供下一次真实搜索前比较；旧日志没有这些元数据，不能据此断言真实账号具体丢了哪条 Cookie。

### 8.4 取昵称

- Mekke：登录成功后打开 `https://www.goofish.com/personal`（不带 `userId`），等卖家头部接口（15 秒），取 `data.module.base.displayName` 作为昵称、`data.module.base.avatar.avatar` 作为头像（字段见 9.4 节）。这个页面会显示自己的资料，上游里**没有依据**，待用真实页面确认。打开它算一次详情类访问。

## 九、数据解析

### 9.1 通用规则

- 解析函数是纯函数：输入正文字节，输出结构体或错误。上游的取值函数 `safe_get` 沿路径逐层取，任何一层缺失或类型不对就返回默认值，默认值是 `"暂无"`（`utils.py:51-58`）。我们照这个思路：**字段缺失时用下表的默认值，不报错，不让一个字段坏掉整页**。
- 类型要宽容：数字和数字字符串都要能解析。上游在这点上有 bug（9.2 节的发布时间）。
- 上游的默认值多是给人看的文字（`"未知标题"`、`"地区未知"`）。Kakatta 存空值，显示时再换成对应语言的文字。
- 正文先过 2.4 节的外壳检查，再解析。

### 9.5 价格换算

1. 去掉「当前价」、`¥`、`￥`、逗号和首尾空白（上游只去「当前价」和 `¥`，`parsers.py:27,30`）。
2. 含「万」时，去掉「万」后乘以 10000，例如 `1.2万` → 12000（`parsers.py:30`）。上游换算后写回成 `¥12000` 这样的文字，四舍五入到整数。
3. 剩下的不是合法数字就当作未知价格，不报错。上游在含「万」又不是合法数字时会抛异常，让整页解析失败。
4. 用十进制解析后存成整数的「分」，避免浮点误差；比较价格区间时也用分。

### 9.6 发布时间

- `args.publishTime` 是毫秒时间戳。上游只认字符串：先判断是不是全数字，是就除以 1000 转成服务器本地时间，格式 `%Y-%m-%d %H:%M`，否则写「未知时间」（`parsers.py:59`）。如果这个字段是数字，上游的 `.isdigit()` 会抛异常，整页解析失败。
- Kakatta：字符串和数字都接受，转成整数毫秒，用 `time.UnixMilli` 得到时间点，按 UTC 存储。显示时按服务端配置的时区（`DECISIONS.md` 第 15 条）。
- 本地补筛「N 天内」时用时间点直接比较，不受时区影响（5.7 节）。

### 9.7 链接

- **网页链接**：`main.targetUrl` 以 `fleamarket://` 开头时，把这个前缀换成 `https://www.goofish.com/`，例如 `fleamarket://item?id=123456` → `https://www.goofish.com/item?id=123456`（`parsers.py:58`）。不是这个前缀的原样保留。
- **手机 App 链接**（`utils.py:105-114`）：从网页链接里用正则 `item\?id=(\d+)` 取出商品 ID，拼成
  `https://pages.goofish.com/sharexy?loadingVisible=false&bft=item&bfs=idlepc.item&spm=a21ybx.item.0.0&bfp=` + URL 编码后的 `{"id":<商品ID>}`。
  例如商品 ID 123456 → `bfp=%7B%22id%22%3A123456%7D`。上游用 Python 的 `quote`，Go 里用 `url.QueryEscape` 结果一样。商品 ID 是纯数字时 JSON 里写数字，不加引号；取不到 ID 时上游返回原来的网页链接。Mekke 直接用 9.2 节的商品 ID 拼，不再从链接里取，结果相同。
- **去重**：用商品 ID。上游用「链接里第一个 `&` 之前的部分」（`utils.py:117-119`），链接格式一变就会失效。

### 9.8 注册时长

`sellerDO.userRegDay` 是注册天数，换算成「来闲鱼 X 年 Y 个月」（`utils.py:131-156`）：

1. 不是正整数时显示「未知」。上游只接受整数类型，数字字符串也显示「未知」；我们也接受数字字符串。
2. 年 = 向下取整（天数 ÷ 365.25）。
3. 月 = 四舍五入（（天数 − 年 × 365.25）÷（365.25 ÷ 12））。上游用 Python 的 `round`，遇到正好 .5 时取偶数，Go 里用 `math.RoundToEven` 才完全一致。
4. 月等于 12 时，年加 1，月变 0。
5. 文字：年和月都大于 0 →「来闲鱼 X 年 Y 个月」；只有年 →「来闲鱼 X 年整」；只有月 →「来闲鱼 Y 个月」；都是 0 →「来闲鱼不足一个月」。英文界面用同样的规则翻译。

## 十一、待用真实页面确认的事项

由作者在动工前的实验里用实验账号确认（`EXPERIMENT.md`）。实验是半自动的：实验工具按正式流程跑一次（1 次搜索加 2–3 个详情），作者在远程画面里看着，出现验证自己处理；工具的日志能顺带验证选择器、中文输入和接口解析。确认时只在实验本来就要做的访问里顺便看，不为了确认多跑搜索或多开详情。

**通用方法**：在实验用的那个 Chrome 窗口里，作者自己按 F12 打开开发者工具（人手操作，不是程序注入）：
