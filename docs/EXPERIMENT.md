# 动工前的实验

目的：用真实的闲鱼账号验证 `CRAWL-POLICY.md` 第八节列出的几个假设，再给抓取方案定稿。实验程序不对外发布，只在作者自己的电脑上运行。

## 实验程序：`kakatta-probe`

一个命令行程序（`cmd/kakatta-probe`）。它用到的浏览器控制、闲鱼流程、风控识别和节奏控制，都放在正式代码的包里（`internal/browser`、`internal/xianyu`、`internal/pacer`），以后正式版直接复用，不写一次性的代码。

它只做实验需要的事：不调用 AI，不发推送，不写数据库，结果写进本地的日志文件。

### 命令

- `kakatta-probe login`：打开一个有界面的 Chrome，使用实验专用的浏览器配置目录，进入闲鱼首页，由作者自己扫码登录。程序只检查登录用的 Cookie 在不在，不读取、不打印 Cookie 的值。确认登录成功后，记下昵称和时间，然后关闭浏览器。
- `kakatta-probe run`：按参数循环运行。每一轮：
  1. 启动 Chrome；
  2. 在首页停留并滚动；
  3. 在搜索框里输入关键词；
  4. 读第 1 页结果；
  5. 挑最新的几个商品打开详情；
  6. 关闭 Chrome；
  7. 等到下一轮。

  每一步都按 `CRAWL-POLICY.md` 的等待时间来。任何一步出现风控信号，**立即结束整个程序**，不重试，把当时的情况写进日志，等作者决定下一步。
- `kakatta-probe check`：只打开首页，检查登录状态还在不在。用来测登录状态能保持多久，每次只访问一个页面。

### 参数（默认值按新号实验方案）

| 参数 | 默认值 |
|---|---|
| 关键词 | 必填 |
| 运行间隔 | 60 分钟，随机延长 0–30% |
| 每轮翻页 | 1 页 |
| 每轮最多打开几个详情页 | 3 个 |
| 不运行的时段 | 22:00–08:00 |
| 总共跑多久 | 7 天 |
| 每小时和每天的访问上限 | 按 `CRAWL-POLICY.md` 第六节的默认值 |

### 记录什么

日志是一行一条的 JSON 文件，每条都带时间：

- 每次页面跳转和点击：做了什么、等了多久、对应的接口是否成功（`ret` 的值）、耗时。
- 每一轮的汇总：搜到几个商品、打开了几个详情、耗时。
- 风控事件：哪种信号、出现在哪一步、触发前这一轮做了什么。
- 登录状态：每轮开始时登录是否还在。
- 资源占用：Chrome 所有进程加起来的内存峰值，浏览器配置目录的大小。

### 三个环境，依次运行，同一时间只跑一个

1. **Mac 直接运行**：用本机安装的 Google Chrome。
2. **Mac 上的 Docker**：Linux 容器里跑 Google Chrome 加 Xvfb，验证服务器那条路。需要扫码或过验证时，容器里启动 x11vnc 和 noVNC，作者在 Mac 的浏览器里打开 noVNC 页面操作。这个阶段的浏览器配置目录和第 1 阶段不同，要重新扫码登录一次。
3. **Windows 直接运行**：用本机安装的 Google Chrome，没有就用 Edge。

每个阶段各跑一周。前一阶段触发了验证的话，先按 `CRAWL-POLICY.md` 第四节冷却，再决定要不要调参数继续。

### 实验回答哪些问题

| `CRAWL-POLICY.md` 第八节的问题 | 怎么回答 |
|---|---|
| 1. 按默认值跑多久会触发验证 | 三个环境的风控事件记录 |
| 2. 登录状态能保持多久 | 每轮开始时的登录检查 |
| 3. 手动拖滑块能不能通过 | 只有真的出现滑块时才能测：Mac 上直接拖，Docker 里通过 noVNC 拖，记录结果 |
| 4. 实际的内存和硬盘占用 | 资源占用记录，加上 Docker 镜像的实际大小 |
| 5. 搜索框输入和直接打开网址有没有区别 | **这次不测**：只有一个账号，同时比较两种做法要么得换号，要么得在同一个号上多冒一次险。默认采用搜索框输入（有其他项目的实测支持），以后有更多账号时再比较 |

### 开发时怎么测实验程序

开发和测试都不访问闲鱼。用一个本地的假闲鱼页面（静态 HTML，加上照上游源码字段构造的接口样例），在本机 Chrome 里跑完整流程，确认页面操作、接口读取、风控识别和节奏控制都正确。只有作者运行 `login` 和 `run` 时才会访问真实的闲鱼。
