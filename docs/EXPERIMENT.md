# 动工前的可行性实验

目的：动工前粗看几件只有真实环境才能回答的事，确认这条路走得通（`DECISIONS.md` 第 37 条）。不是长时间跑频率测试，也不是写一个完整的程序。

## 在哪里做

作者 Mac 上的 Docker（Linux 容器，Google Chrome + Xvfb，需要操作时用远程画面）。有条件的话，再在一台 NAS 或云服务器上做一次第 1、5 项。客户端已经搁置（`DECISIONS.md` 第 36 条），所以不在 Mac、Windows 上直接跑。

账号：作者提供的新号，按 `CRAWL-POLICY.md` 第八节「新号怎么用」：先养号 1–2 周，实验时访问量很小，分几天做，只在白天。

## 要回答的问题

每一项都是作者在远程画面里手动或半手动做几次，总共几十次页面访问。

| # | 问题 | 怎么看 | 算走通的标准 |
|---|---|---|---|
| 1 | Docker 里的 Chrome 能不能正常用闲鱼 | 扫码登录，在首页搜索框里搜一个词，打开两三个详情。WebGL「不开」和「llvmpipe」各做一次，中间隔几小时 | 两次里至少一种设置没出现「非法访问」、验证码或登录跳转 |
| 2 | `XIANYU.md` 第十一节里待确认的页面细节 | 做第 1 项时顺便看：搜索框的选择器、回车后是不是在同一个标签页跳到结果页、登录 Cookie 是不是 `unb`、详情的描述字段在哪 | 每一条都有结论，写回 `XIANYU.md` |
| 3 | 登录能保持多久 | 登录后重启一次容器，看还在不在；之后每天只打开一次首页看，持续一周左右 | 重启后还在；一周内大部分时间还在（参考项目导入 Cookie 的方式只能撑几十分钟到几小时，#492） |
| 4 | 手动能不能过滑块 | 不主动去触发。真的遇到时，分别在电脑浏览器和手机浏览器里通过远程画面拖 | 至少电脑上能过 |
| 5 | 实际占多少资源 | 看镜像实际大小、闲鱼搜索页和详情页的内存峰值；不加 `--disable-dev-shm-usage` 时内存是否确实更少；默认 compose 设置下沙盒能不能起来；浏览器运行时有没有 `chrome_crashpad_handler` 进程；关掉浏览器后有没有残留进程和僵尸进程，空闲时 CPU 占用多少 | 数字写回 `DECISIONS.md` 第 16、38 条；有 crashpad 或残留进程时按第 46 条处理 |

## 不在这次回答的

- 按默认频率跑多久会触发验证：一个号、几天时间测不出可靠的阈值（`CRAWL-POLICY.md` 第八节）。
- 搜索框输入和直接打开搜索网址的区别。
