# 动工前的可行性实验

目的：动工前粗看几件只有真实环境才能回答的事，确认这条路走得通（`DECISIONS.md` 第 37 条）。不是长时间跑频率测试，也不是写一个完整的程序。

## 在哪里做

作者 Mac 上的 Docker（Linux 容器，Google Chrome + Xvfb，需要操作时用远程画面）。有条件的话，再在一台 NAS 或云服务器上做一次第 1、5 项。客户端已经搁置（`DECISIONS.md` 第 36 条），所以不在 Mac、Windows 上直接跑。

账号：作者提供的新号，按 `CRAWL-POLICY.md` 第八节「新号怎么用」：先养号 1–2 周，实验时访问量很小，分几天做，只在白天。作者 2026-11-10 确认新号已经准备好。

## 要回答的问题

做法统一是**半自动**：每次实验由实验工具按正式流程跑一次（1 次搜索加 2–3 个详情），作者在远程画面里看着，出现验证自己处理。访问量和作者手动浏览一样，但能顺带验证选择器、中文输入和接口解析。扫码登录、过滑块这类本来就要人做的，作者在远程画面里自己做。总共几十次页面访问。

### 可选的内存对照

保持架构、Chrome 版本、分辨率、页面、正常操作和测量时长一致，分别持续观察 `docker stats`，记录观测到的最高内存、稳态值、浏览器进程数和页面异常。一次 `--no-stream` 输出不能当作峰值。进程限制不是固定进程数量的保证，不关闭站点隔离，依据见第 121 条。

实验前后，由作者自己打开同一份本地指纹检测页，核对平台、UA、Client Hints、语言、时区、屏幕、WebGL 和媒体能力；有差异就记录，不把少数属性相同当作所有网页行为完全相同。自动容器测试不访问外部检测站。Mac Docker 的 arm64 结果不替代 amd64 的真实验收，浏览器自身的平台简化值也不由 Kakatta 改写。

当前实验工具没有通用的附加 Chrome 参数入口。这项只记录可选方法；开展前另行准备只增加上述两个参数的独立实验构建，由作者启动，不修改正式默认值，不写不存在的命令。真实闲鱼的访问仍按原流程一次运行、限频并在验证时停手，不为测内存额外循环抓取。

## 不在这次回答的

- 按默认频率跑多久会触发验证：一个号、几天时间测不出可靠的阈值（`CRAWL-POLICY.md` 第八节）。
- 搜索框输入和直接打开搜索网址的区别。

## 需要的工具

做实验要一个装好 Chrome、Xvfb、远程画面的容器，加一个实验工具：按正式流程跑一次搜索和 2–3 个详情，把每一步找没找到元素、结果页网址、接口解析出的字段写进日志。**这些等讨论全部确认结束、作者说开始写之后再做。** 仓库里现有的 `cmd/kakatta-probe` 是 2026-11-10 违反「讨论阶段不写代码」提前写的，而且是按「长时间循环跑」的错误理解写的；开始写代码时删掉，实验工具照本文重写（`DECISIONS.md` 第 57 条）。

## 实验结果

实验工具位于 `cmd/experiment/`，容器启动、参数、设置文件及断网回归说明见 [CONTAINER.md](CONTAINER.md)。开发验证只用本地假页面；下面仍只记录作者完成的真实环境实验。

扫码前页面报告登录失效时，工具保留当前浏览器等待扫码。接口日志使用程序识别的状态，结果页网址只保留用于核对的 `q`，主图网址省略认证信息、查询参数和片段。

2026-11-11，作者在 Mac 的 OrbStack 容器里完成首次真实扫码：15:09:54 打开登录首页，15:10:18 登录框消失，15:10:21 取得自己的资料并记录登录完成。下一次搜索在 15:14:18 打开首页后仍出现登录框，旧 `unb` 存在。该次没有走到搜索，不把扫码完成当作重开后登录保持已通过。

这次触发第 130 条修正：保留会话 Cookie 的同时禁止恢复旧网页；旁路接口会话失效只作观察，同一响应跨步骤去重。下一次真实验证要先重新构建、扫码，再按原账号间隔另开一次搜索；对比登录摘要的 `observations.cookie_metadata` 中 `after_login`，与搜索摘要中导航前的 `after_startup`。只比较名称、域、会话标记和到期时间；元数据未知时先排查读取失败，不能当作 Cookie 已丢失。真实登录续期、搜索和后续详情仍待作者复测。

2026-11-11 16:28 再次复测：导航前的元数据中仍有会话 Cookie，但旧持久 `unb` 也在。登录框延迟出现，旧判定在等待 250 毫秒后提前结束，作者尚未扫码，随后自己的主页前检查才报告可见登录框。该现象不否定上一轮 Cookie 保留修复，证明的是 `unb` 不能判断会话有效。

第 131 条已取消 Cookie 成功条件和「尚未见失效」捷径，改为本会话见框、关框和新页面活动。下一次真实扫码要核对 `login_refresh` 与 `login_header`：前者保留本次变化，后者分阶段记录安全结构。现有未登录页面也有头像，已登录首页的正面选择器仍待真实样本；找不到可靠节点时继续等待，不提前完成。仍需作者重新构建、扫码，再按原间隔进行单次搜索；不为补证据增加额外访问。

### 第二轮：扫码、重开和单次搜索已走通

2026-11-11，作者使用构建 `3f91b46`、Chrome `157.0.8103.50`，17:32 完成扫码登录；17:37 另开搜索会话，仍是登录状态。搜索「相机」并筛选，解析 30 条，随后 3 个详情成功，17:39 结束；两次会话均无风控信号和诊断包。登录摘要为 `summary-20261111-173247-3340176200/summary.json`，搜索摘要为 `summary-20261111-173905-1459185449/summary.json`，均位于该实验账号的 `logs/summaries/` 下，事件位于当天 JSONL。

本轮补足了上一段等待的首页样本：用户区 `nick--` 节点由「登录」变为非空昵称，头像则登录前后都有；扫码后登录框消失、主框架导航并重发 mtop。第 132 条据此为扫码路径再加正面节点，并允许有正面节点且无未处理风险的已有登录完成，不靠 Cookie 存在或固定等待推定成功。第 130 条的同一浏览器启动入口已在本次真实重开验证中生效；不将这一次结果写成一周续期已通过。

其他已确认事实及范围写入 `XIANYU.md` 第十一节。尚有三个字段缺口：5 条搜索昵称为空；第三个详情的芝麻信用文字为空；自己的主页商品数路径不可得。成功响应没有保存原文，暂不能判定缺失原因，解析器保持原路径及未知值。第 133 条只在下次原定流程遇到同类缺失时保存有限字段结构，不保存值、不增加访问。网页空昵称用中英文提示兜底，通知沿用原格式。

下次作者自然运行时核对新增昵称条件和缺失字段观察即可，不为补证据另开搜索。地区点击请求、已售或下架状态、交易信用等级映射、评价时间、自己的主页本人身份及长期登录保持仍按原计划确认；本轮没有验证这些项目。
